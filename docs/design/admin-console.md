# 設計: 管理者向けの管理画面（リポジトリから作るカタログ）

- 状態: **設計（作るのはまだ）**。2026-11-24 に設計。[15 章](#15-決めること確かめること)の決めることを利用者が決めてから、[14 章](#14-作る順番pr-の分け方)の順で PR に分けて作ります。決まった形は、作る PR で [reference.md](../reference.md) と [deploying.md](../deploying.md) に書きます。
- このフォルダ（`docs/design/`）のファイルは、ドキュメントのサイトのページになりません。
- 関係する設計: [行レベル制御](row-level-security.md)（閲覧の記録に、同じ「利用者」を使う）、[SQL のデータセット](sql-datasets.md)（管理画面に、データセットのパラメーターを並べる）。

## 1. 何をするか

DevBI のダッシュボードは、git のリポジトリのファイルです。ダッシュボードとフォルダ（プロジェクト）が増えると、「何がどこにあり、だれがいつ変え、本番ではどこで開けて、どれくらい見られているか」が、リポジトリを読まないとわからなくなります。そこで、**リポジトリから管理者向けの管理画面を作るコマンド** `devbi-catalog` を足します。

```sh
npx @devbi/catalog --out catalog     # リポジトリのルートで。catalog/index.html ができる
```

- リポジトリの中の DevBI のプロジェクトを決まり（[5 章](#5-プロジェクトを見つける決まりフォルダ-1-つで-1-画面)）で見つけ、**フォルダ 1 つを 1 画面**にします。ダッシュボード、指標、SQL（データセット）、行レベル制御の決まりと、それらのつながりを並べます。
- **変更の履歴は、手元の clone の `git log` から作ります。** GitHub の API は使いません。リモートが GitHub でも、Azure DevOps でも、社内のサーバーの bare リポジトリでも、同じように動きます。リモートごとに変わるのは、コミットやファイルへのリンクの書き方だけです（[8 章](#8-リモートへのリンク)）。
- ダッシュボードごとに、**本番の画面へのリンク**を置きます（置いた場所の URL は設定に書く。[9 章](#9-公開先へのリンク)）。
- **閲覧数**は git にないので、別の仕組みにします。DevBI のサーバー（`devbi-serve`、Node、C#）が「だれが・どのダッシュボードを・いつ開いたか」を記録し、管理画面がそれを数えて出します（[10 章](#10-閲覧数)）。
- **見るだけの画面**です。管理画面から dash.json などを書き換えることはしません。直すときは、今と同じく GUI エディタかファイルを直してコミットします。管理画面には、そのためのリンク（リモートのファイルの画面）と手順を出します。

できるもの（ファイル 1 つで開ける静的なサイト）は、CI かサーバーのタスクで作り、社内の Web サーバーやファイル共有の、**管理者だけが入れる場所**に置きます（[12 章](#12-置き場所と見られる人)）。

## 2. だれ向けで、何に答えるか

### 2.1 管理者向け

DevBI のプロジェクトを預かる人（情報システムの担当、レポートをまとめて見ている開発者）向けです。業務の人が「どのレポートを見ればいいか」を探す画面ではありません（それは今の `DevbiApp` の一覧と、社内のポータルの役目です）。SQL の中身や、行レベル制御の決まり（だれにどの行を見せるか）まで載せるので、見せる相手は管理者にしぼります。

### 2.2 答えたい問い

| 問い | 管理画面で見るところ |
| --- | --- |
| どのフォルダに、どのダッシュボードと SQL があるか | 全体の画面のプロジェクトの一覧、プロジェクトの画面 |
| だれが、いつ、何を変えたか | 変更の履歴（全体、プロジェクトごと、ダッシュボードごと） |
| 本番ではどこで開けるか | ダッシュボードの「本番で開く」 |
| どれくらい見られているか。しばらくだれも見ていないものはどれか | 閲覧数の画面 |
| この SQL や指標ファイルを変えると、どのダッシュボードに響くか | ダッシュボードの「つながり」、SQL の「使っているダッシュボード」 |
| だれにどの行が見えるか | プロジェクトの画面の「行レベル制御」 |
| どのダッシュボードも使っていないのに、API からは読める SQL はどれか | SQL の一覧の「使っていません」 |

### 2.3 正はいつも git

管理画面は、リポジトリのある時点（`main` のあるコミット）から作った**写し**です。画面の上に「main の 3f2a1c9（2026-11-24 10:00）の時点」と出します。管理画面の中で編集できるようにすると、git の外に 2 つめの正ができてしまうので、v1 は見るだけにします。

[handoff.md](../handoff.md) の「範囲外」にある「全社ガバナンス」（Power BI の管理ポータルのような、権限やテナントの設定）は、範囲外のままです。この管理画面は、リポジトリの中身と閲覧の記録を**見る**だけで、権限を変えたり、利用者を管理したりはしません。

## 3. 範囲

v1 で作るもの:

- 新しいパッケージ `@devbi/catalog` と、コマンド `devbi-catalog`: リポジトリ → 管理画面（`index.html` 1 つ）と `catalog.json`
- プロジェクトを見つける決まりと、設定ファイル `devbi-catalog.yaml`（書かなくても動く）
- 画面: 全体、プロジェクト（フォルダごと）、ダッシュボード、変更の履歴、閲覧数
- git の履歴（`git log`）と、GitHub・Azure DevOps・GitLab へのリンク（ほかはリンクの形を設定に書く。リンクなしでも動く）
- 閲覧の記録: ブラウザが「開いた」を API に送り、`devbi-serve`・Node（Next.js など）・C# がファイルに書く。`devbi-catalog` がそれを数える
- CI（GitHub Actions、Azure Pipelines）と、社内サーバーのタスクでの作り方（deploying.md に書く）

v1 で作らないもの（あとで考える）:

- 管理画面からの編集や PR づくり（v1 は、リモートのファイルの画面へのリンクまで）
- 静的なサイト（IIS などがファイルを配るだけの置き方）の閲覧数。Web サーバーのアクセスログから数える形を [10.7](#107-静的なサイトの閲覧数あとで) にメモします
- 本番に出ている版（どのコミットをビルドしたものか）との比べ（[14 章](#14-作る順番pr-の分け方)の 6）
- `devbi-check` の結果を載せること（データベースにつながらない CI でもできる、ファイルの検査だけ）
- コミットの差分（変わった行）を載せること（v1 は変わったファイルまで。差分はリモートの画面で見る）
- GitHub や Azure DevOps の API を使うもの（PR のレビューの状態、だれが承認したか）

## 4. 全体の形

```
リポジトリ（GitHub / Azure DevOps / 社内サーバーの bare リポジトリ）
   │  CI の clone か、サーバーの上の clone・bare リポジトリそのもの
   ▼
devbi-catalog ── 1. コミットしたファイルを git から読む
   │             2. プロジェクトを見つけて、中身とつながりを読む
   │             3. git log を 1 回読んで、プロジェクトとダッシュボードに振り分ける
   │             4. （あれば）閲覧の記録を数える
   ▼
catalog/index.html（管理画面。データも中に入れたファイル 1 つ） ＋ catalog.json（機械が読む形）
   │
   ▼ 管理者だけが入れる場所に写す（IIS の Windows 認証、ファイル共有のアクセス権など）


本番のブラウザ ──「sales を開いた」──▶ devbi-serve / Node / C#（POST api/view）
                                          │ 利用者は、行レベル制御と同じもの
                                          ▼
                                     views/2026-11-24.jsonl ──▶ devbi-catalog（上の 4 で数える）
```

閲覧の記録は本番のサーバーにあり、リポジトリにはありません。管理画面を本番のサーバーの上で作るときは、`devbi-catalog` に記録のフォルダを渡します。CI で作るときは、サーバーで記録を数えたファイル（`views.json`）を、管理画面から読める場所に置きます（[10.5](#105-数える)）。

## 5. プロジェクトを見つける決まり（フォルダ 1 つで 1 画面）

### 5.1 決まり

**`dashboards/` の直下に `*.dash.json` が 1 つ以上あるフォルダを、1 つのプロジェクトにします。** `@devbi/vite` の `dir`（`dashboards/`・`models/`・`data/`・`api/` のあるフォルダ）と同じ場所です。設定は要りません。

このリポジトリなら、次の 4 つが見つかります。

| フォルダ | ダッシュボード |
| --- | --- |
| `examples/sales` | 6 |
| `examples/sales/e2e/rls` | 1 |
| `examples/oss` | 1 |
| `packages/create-devbi/template` | 1（雛形なので、設定の `exclude` で外す） |

- プロジェクトの中にプロジェクトがあるとき（`examples/sales` の中の `examples/sales/e2e/rls`）は、別々のプロジェクトです。外側の履歴には、内側のファイルの変更を入れません。
- プロジェクトの名前は、設定（[11 章](#11-設定ファイルdevbi-catalogyaml)）の `title`、なければフォルダの名前です。
- ダッシュボードの名前はファイル名（`sales.dash.json` なら `sales`。画面の URL の `#/sales`）、見出しは dash.json の `title` です。
- プロジェクトのフォルダか、その上のフォルダ（リポジトリの中だけ）のいちばん近い `package.json` から、パッケージの名前と DevBI のパッケージの版（`devbi`・`@devbi/*` に書いた範囲）を読みます。プロジェクトごとに版が違えば、全体の画面に出します。

### 5.2 読むのは、コミットしたファイルだけ

`devbi-catalog` は、作業フォルダではなく、**ある ref（既定は `HEAD`）のコミットの中身**を、`git ls-tree` と `git cat-file --batch` で読みます。

- git に入れないファイル（`.env.local` のパスワード、`dist/`、`node_modules/`）と、コミットしていない変更は、管理画面に入りません。
- 作業フォルダが要らないので、社内サーバーの bare リポジトリでもそのまま動きます（`--repo C:\git\reports.git --ref main`）。
- 読んだ中身は、`devbi-check` と同じ読み込み（`@devbi/vite` の `readProject`、`@devbi/server` の `parseDataset`）に渡します。読み方が 2 通りにならないようにするためです。今の読み込みはフォルダから読むので、一時フォルダに書き出して渡すか、ファイルを読む部分を差し替えられるようにします（作るときに決める）。
- `.env`（git に入れてよい接続先）からは、接続先の変数の名前（`DEVBI_DB`、`DEVBI_DB_HR`）と、データベースの種類（`mssql`、`pg` など、URL の先頭）だけを読みます。URL の残り（サーバー名、ユーザー名）は管理画面に入れません。

### 5.3 読めないファイルがあっても止めない

1 つの dash.json が読めなくても、管理画面は作ります。そのダッシュボードには「読めません: tiles[3]: x がありません」のように出し、全体の画面の「問題」に数えます。`--strict` を付けたときだけ、読めないファイルがあれば終了コード 1 で止めます（CI で気づきたいとき）。

## 6. 画面

画面は 5 つです。URL は管理画面の中の `#/…` で、ほかの画面からリンクを貼れます。

### 6.1 全体

```
DevBI 管理画面                                   main 3f2a1c9 の時点（2026-11-24 10:00）

プロジェクト 3 ・ ダッシュボード 8 ・ SQL 8 ・ この 30 日の変更 12 ・ この 30 日に開かれた回数 1,284 ・ 問題 1

プロジェクト
  場所                      名前          ダッシュボード  SQL  行レベル制御  最後の変更          30 日の閲覧
  examples/sales            売上          6               6    なし          11-23 山田（#41）    1,102
  examples/sales/e2e/rls    担当別の売上  1               2    あり          11-23 山田（#41）      182
  examples/oss              OSS の統計    1               0    なし          11-15 鈴木（#27）        —

最近の変更
  11-23  examples/sales/e2e/rls  行レベル制御: Next.js の見本で、アプリのログインから利用者を渡す（#41）  山田
  11-23  examples/sales          ファイル出力をメニューにまとめる（#35）                              山田
  …
```

- プロジェクトの一覧は、フォルダの木の形でも並べられます（モノレポの形を見るため）。
- 「問題」は、読めないファイル、どのダッシュボードも使っていない SQL、プロジェクトどうしで違う DevBI の版、浅い clone で履歴が途中まで、などの数です。

### 6.2 プロジェクト（フォルダごと）

1 つのフォルダの、次のものを 1 つの画面に並べます。

- **見出し**: 名前、場所、本番の場所へのリンク、リモートのフォルダへのリンク、担当（設定の `owner`、なければこの 1 年によく変えた人の上位 3 人）、パッケージの名前と DevBI の版
- **ダッシュボード**: 名前（URL）、見出し、タイルの数、使う指標ファイル、データの元、最後の変更、30 日の閲覧数、「本番で開く」
- **指標ファイル**（`models/*.metrics.yaml`）: 指標と軸の数、データの元（`data/` の Excel・CSV、`read_api` の SQL、URL）、使っているダッシュボード
- **SQL（データセット）**（`api/*.sql`）: 名前、説明、接続先（`-- connection:` の名前）、パラメーター（`-- param:`）、`-- roles:`・`-- access:`、`-- snapshot:` の時刻、使っているダッシュボード。どのダッシュボードも使っていない SQL には「使っていません（API からは読めます）」と出します（[ログインと、データが見える範囲](../deploying.md#ログインとデータが見える範囲)のとおり、置いた API に届く人は、どの SQL でも読めるため）。SQL の中身も開いて読めます（`--no-sql` で載せない）
- **行レベル制御**: ファイルから見た行レベルのモード（[行レベル制御の 6.4](row-level-security.md#64-行レベルのモード絞り忘れを止める) の文字の検索と同じ決め方。ホストの `requireUser` はリポジトリからはわからないので、「ファイルから見ると」と書く）、SQL ごとの `:user.` の属性・`-- roles:`・`-- access: all`、`access/user.sql` があるか。役割ごとに、読める SQL の一覧も出します
- **データのファイル**（`data/`）: 大きさと、最後に変えたコミット（Excel をコミットして新しくしているなら、データの更新の履歴になる）
- **変更の履歴**（このプロジェクト）

### 6.3 ダッシュボード

- タイルの一覧（種類、見出し、指標・軸・データセット、自作タイルのファイル）
- **つながり**: ダッシュボード → 指標ファイル → データの元（`data/` のファイル、`read_api` の SQL）→ 接続先の名前。データセットのタイル（`query.dataset`）は、ダッシュボード → SQL → 接続先
- **変更の履歴**: このダッシュボードのファイル（dash.json と、`dashboards/<名前>/` の自作タイル）の変更と、つながっているファイル（指標ファイル、SQL、データのファイル）の変更。どちらの変更かを印で分けます
- **閲覧数**: 日ごとのグラフ、7・30・90 日の回数と人数
- **リンク**: 本番で開く、リモートでファイルを見る、手元の GUI エディタで直す手順（`cd examples/sales && npm run dev` で開き、`http://localhost:5173/#/sales` の「編集」）

### 6.4 変更の履歴

全体の履歴を、プロジェクト・人・期間で絞って見る画面です。1 行が 1 つのコミット（[7.1](#71-読み方) のとおり、main に入った単位）で、日時、人、見出し、PR の番号（リンク）、変わったプロジェクトとファイルを出します。消したダッシュボードと名前を変えたダッシュボードも、ここに出ます（「sales-old を消した」「sales-db を sales-database に名前を変えた（前の URL `#/sales-db` は開けなくなった）」）。

### 6.5 閲覧数

閲覧の記録があるときだけ出ます（[10 章](#10-閲覧数)）。

- よく開かれている順（7・30・90 日の、開いた回数と見た人の数）
- **しばらくだれも開いていないダッシュボード**（90 日で 0 回など。片付けの候補）
- ダッシュボードごとの、日ごとのグラフ
- 見た人の名前は、既定では出しません（[10.6](#106-だれが見たかを残すか)）

## 7. 変更の履歴（`git log` から）

### 7.1 読み方

`git log` を 1 回だけ流して全部のコミットを読み、それからプロジェクトとダッシュボードに振り分けます（ファイルごとに `git log` を流すと、ダッシュボードが多いときに遅いため）。

```sh
git -c core.quotePath=false log --first-parent -M --name-status -z --use-mailmap --format=<番号・日時・人・見出し・本文> HEAD
```

- **`--first-parent`**: main に入った単位（1 つの PR）で 1 行にします。Azure DevOps の既定の取り込み方（マージ コミットを作る）では、PR の中の細かいコミットが全部並んで読みにくいためです。マージ コミットで変わったファイルは、1 つめの親との違いで数えます。GitHub の squash（このリポジトリ）では、今と同じ 1 PR 1 コミットです。
- **`-z` と `core.quotePath=false`**: 日本語のファイル名を `"\346\227\245…"` のような形にせず、そのまま読みます。
- **`-M`**: 名前の変更を見つけます（`R` の行）。
- **`--use-mailmap`**: 同じ人がパソコンごとに違う名前やメールアドレスでコミットしていても、`.mailmap` があれば 1 人にまとめます。
- 日時は、コミットが main に入った時刻（committer の日時）を出し、書いた人（author）と入れた人（committer）が違えば両方を出します。時刻は、管理画面を見ているパソコンの時間帯で出します。

### 7.2 振り分け

- 変わったファイルは、そのファイルを含むいちばん内側のプロジェクトに入れます（`examples/sales/e2e/rls/api/x.sql` は `examples/sales/e2e/rls` だけ）。
- ダッシュボードの履歴は、`dashboards/<名前>.dash.json` と `dashboards/<名前>/` の変更と、つながっているファイル（[6.3](#63-ダッシュボード)）の変更です。つながりは今のコミットのもので見ます。途中で指標ファイルを変えたダッシュボードでは、前の指標ファイルの変更は入らず、つなぐ前の今の指標ファイルの変更は入ります。
- 名前の変更は、新しいほうから古いほうへたどって、今のダッシュボードの履歴につなげます。
- 消したダッシュボードは、プロジェクトの履歴に「消した」と出し、消す前の最後のコミットへのリンクを置きます。

### 7.3 浅い clone

CI の clone は、**最後のコミットだけの浅い clone** のことがあります（GitHub Actions の `actions/checkout` は既定で 1 コミットだけ。Azure Pipelines も、新しいパイプラインは既定で浅いことがあります）。浅い clone の `git log` は途中で切れるので、そのままでは履歴が足りないことに気づけません。

- `devbi-catalog` は `git rev-parse --is-shallow-repository` で確かめ、浅いときは管理画面の上と全体の「問題」に「履歴が途中までです（浅い clone）」と出します。`--strict` では止めます。
- CI の例（[12.3](#123-作り方の例)）には、`fetch-depth: 0`（GitHub Actions）と `fetchDepth: 0`（Azure Pipelines）を書きます。

### 7.4 量

- 載せるコミットは、既定で新しいほうから 5,000 個まで（`--max-commits`）。プロジェクトの最後の変更や「よく変えた人」は、その範囲で数えます。
- コミットごとに載せるのは、プロジェクトの中のファイルの変更だけです（プロジェクトの外のファイルだけを変えたコミットは載せない）。
- メールアドレスは、既定では載せません（名前だけ。`--emails` で載せる）。

## 8. リモートへのリンク

### 8.1 見分け方

`git remote get-url origin`（`--remote` でほかの名前にできる）の URL から、Web の画面の場所を作ります。

| リモートの URL | 見分けた種類 | Web の場所 |
| --- | --- | --- |
| `https://github.com/o/r.git`、`git@github.com:o/r.git` | GitHub | `https://github.com/o/r` |
| `https://dev.azure.com/org/proj/_git/repo`、`https://org@dev.azure.com/org/proj/_git/repo` | Azure DevOps | `https://dev.azure.com/org/proj/_git/repo` |
| `git@ssh.dev.azure.com:v3/org/proj/repo` | Azure DevOps | 同じ |
| `https://org.visualstudio.com/proj/_git/repo` | Azure DevOps（古い URL） | そのまま |
| `https://tfs.corp.local/tfs/DefaultCollection/proj/_git/repo` | Azure DevOps Server（社内に置く形） | そのまま（パスに `/_git/` があれば） |
| `https://gitlab.com/g/p.git` | GitLab | `https://gitlab.com/g/p` |
| `\\server\git\reports.git`、`file:///…`、`ssh://server/srv/git/reports.git` | bare リポジトリ（Web の画面なし） | なし |
| そのほか（GitHub Enterprise Server、社内の GitLab、Gitea など） | 見分けない | 設定に書く（[8.4](#84-自分で書く)） |

### 8.2 リンクの形

| | GitHub | Azure DevOps | GitLab |
| --- | --- | --- | --- |
| コミット | `{web}/commit/{sha}` | `{web}/commit/{sha}` | `{web}/-/commit/{sha}` |
| ファイル | `{web}/blob/{sha}/{path}` | `{web}?path=/{path}&version=GC{sha}` | `{web}/-/blob/{sha}/{path}` |
| フォルダ | `{web}/tree/{sha}/{path}` | `{web}?path=/{path}&version=GC{sha}` | `{web}/-/tree/{sha}/{path}` |
| PR | `{web}/pull/{pr}` | `{web}/pullrequest/{pr}` | `{web}/-/merge_requests/{pr}` |

- `{path}` は、`/` で区切った 1 つずつを URL の形にします（日本語のファイル名のため）。
- ファイルとフォルダのリンクは、管理画面を作ったコミット（`{sha}`）を指します。あとでファイルが変わっても、管理画面と同じ中身が開きます。今の中身を開くための、ブランチ名（`{branch}`）のリンクも出します。
- PR の番号は、コミットの見出しと本文から読みます: GitHub の squash（`… (#41)`）とマージ（`Merge pull request #41 from …`）、Azure DevOps（`Merged PR 123: …`）、GitLab（`See merge request g/p!12`）。
- **Azure DevOps の URL の形は、作るときに確かめます**（特に、社内に置く Azure DevOps Server）。

### 8.3 認証情報を書き出さない

CI では、リモートの URL にトークンが入っていることがあります（`https://user:トークン@dev.azure.com/…`）。`devbi-catalog` は、リモートの URL を**そのまま管理画面に書きません**。8.1 の表で作った Web の場所（ユーザー名とパスワードを除いたもの）だけを書きます。

### 8.4 自分で書く

```yaml
# devbi-catalog.yaml
remote:
  commit: https://git.corp.local/reports/commit/{sha}
  file: https://git.corp.local/reports/src/{sha}/{path}
  folder: https://git.corp.local/reports/src/{sha}/{path}
  pr: https://git.corp.local/reports/pulls/{pr}
```

`remote: none` でリンクを出しません。リンクがないときは、コミットの番号の横に、手元で見るコマンド（`git show 3f2a1c9`）を出します。

## 9. 公開先へのリンク

どこに置いたかはリポジトリからはわからないので、設定に書きます。

```yaml
projects:
  examples/sales:
    title: 売上
    url: https://reports.corp.local/sales/        # dist/ を置いた場所。ダッシュボードは <url>#/<名前>
  reports/hr:
    title: 人事
    url:
      本番: https://app.corp.local/Reports/Hr.aspx?d={dashboard}   # 社内のアプリに埋め込んだ画面
      検証: https://app-test.corp.local/Reports/Hr.aspx?d={dashboard}
```

- `{dashboard}` がなければ、`<url>#/<ダッシュボードの名前>` にします（`dist/` をそのまま置いたとき）。
- 埋め込みで、ダッシュボードごとに画面が違うときは、`dashboards: { sales: https://… }` のように、ダッシュボードごとに書けます。
- いくつも書けば（本番、検証）、全部並べます。

## 10. 閲覧数

### 10.1 なぜ別の仕組みか

- git には、だれが画面を開いたかの記録がありません。
- Web サーバーのアクセスログにも、**どのダッシュボードかは残りません**。ダッシュボードの切り替えは URL の `#` のあと（`#/sales`）で決まり、`#` のあとはブラウザからサーバーに送られないからです。ログに残るのは `index.html` と `assets/` のファイルだけです。
- API のログ（`CORP\yamada api/orders.sql: 1,234 行、85 ms`）は、SQL を読んだ記録です。Excel だけのダッシュボードは API を呼ばず、1 つの SQL を 2 つのダッシュボードが使うこともあるので、ダッシュボードの閲覧数にはなりません。

そこで、**ブラウザが「このダッシュボードを開いた」を API に送り、DevBI のサーバーがファイルに書く**形にします。

### 10.2 ブラウザが送るもの

```ts
// vite.config.ts
devbi({ views: true }); // 既定は false（送らない）
```

- `views: true` でビルドしたダッシュボードは、開いたときに 1 回、`POST <API の場所>view` を送ります。
  - `DevbiApp` で、そのダッシュボードの画面（`#/sales`）に移ったとき。パラメーターや期間を変えたとき、クロスフィルタ、データの読み直しでは送りません（ページを読み込み直したときは、また開いたことになります）
  - 埋め込み（`devbi-embed.js`、`mount`）で、ダッシュボードを置いたとき
- 中身は `{ "project": "examples/sales", "dashboard": "sales", "via": "app" }` です。`project` は、ビルドのときに `@devbi/vite` が、git のルートから見たプロジェクトのフォルダの場所を入れます（git の外でビルドするときは、`views: { project: "reports/sales" }` で書く）。`via` は `app`（`DevbiApp`）か `embed`（埋め込み）です。
- `fetch` の `keepalive` で送り、答えは待たず、失敗しても画面には何も出しません。今の `api/query` と同じく `Content-Type: application/json` で送ります（ほかのサイトのフォームから送れないように）。`view` を知らない古いサーバーは `404` を返すだけです。
- API のない置き方（静的なサイト）では、`views: true` にしません（送っても、受け取るサーバーがない）。静的なサイトの閲覧数は [10.7](#107-静的なサイトの閲覧数あとで) です。
- 開発サーバー（`vite`）では送りません（作っている人の閲覧で数が増えないように）。

### 10.3 サーバーが書くもの

```sh
npx devbi-serve --dir . --view-log D:\devbi\views
```

```json
{"time":"2026-11-24T10:15:03.120+09:00","project":"examples/sales","dashboard":"sales","via":"app","user":"CORP\\yamada"}
```

- 1 回の閲覧が 1 行の JSON（JSON Lines）で、ファイルは 1 日に 1 つ（`2026-11-24.jsonl`。サーバーの時間帯の日付）です。
- `time` はサーバーの時刻です（ブラウザの時刻は使わない）。
- `user` は、**行レベル制御と同じ利用者の ID**（`devbi-serve --user-header`、Node の `{ user }`、C# の `HttpContext.User`）です。ブラウザが送った値は使いません。ログインしていなければ書きません。
- 書く場所を決めたときだけ書きます（既定は書かない）。

| ホスト | 書き方 |
| --- | --- |
| `devbi-serve` | `--view-log <フォルダ>`、`--view-days <日数>`（古いファイルを消す。既定 400 日） |
| Node（`@devbi/server`、Next.js） | `createApiHandler({ views: fileViews(<フォルダ>) })`、または `views: (event) => { … }` で自分の仕組みに渡す（ディスクのない置き場所や、アプリのログ・分析の仕組みに入れたいとき） |
| C#（ASP.NET） | `DevBIOptions.ViewLog = <フォルダ>`、または `OnView = e => …`（Serilog や Application Insights に渡す） |
| 開発サーバー・`vite preview` | 書かない（`204` で答えるだけ） |

- 1 つのフォルダには、1 つのプロセスだけが書きます（2 つの `devbi-serve` や、IIS の複数のワーカー プロセスが同じファイルに書くと、Windows では行が混ざることがあるため）。C# で複数のプロセスになるときは、`OnView` でアプリのログに渡すか、プロセスごとにフォルダを分けます。
- 検証のサーバーの閲覧を数に入れたくないときは、検証と本番でフォルダを分け、本番のフォルダだけを数えます。

### 10.4 守り

`POST api/view` は、DevBI の API で初めての「書く」口です。データベースには何も書きません（データベースのユーザーは今のとおり SELECT だけ）。書くのは、サーバーのフォルダの記録のファイルだけです。

- `project` と `dashboard` は、長さ（200 文字まで）と文字（改行や制御文字がないこと）を確かめ、だめなら `400` です。
- ログインしている人の同じダッシュボードは、1 分に 1 行までにします。ログインしていない人は見分けません（前に IIS や nginx を置くと、全員が同じ IP アドレスに見えるので、IP アドレスで分けると、ほかの人の閲覧まで落としてしまうため）。
- 全部でも 1 分に 600 行、1 日のファイルは 50 MB までにし、超えたら書かずに、サーバーのログに 1 回だけ注意を書きます（ディスクをいっぱいにされないため）。
- 行レベルのモードでは、ほかの API と同じくログインが要ります（`401`）。
- **閲覧数は厳密な記録ではありません。** ログインした人が自分で何度も送れば、数を増やせます（1 分に 1 回まで。ログインのない置き方では、上の全部の上限まで）。ダッシュボードが使われているかの目安に使います。だれがどの行を読んだかの記録は、今の API のログ（SQL ごとの 1 行）のほうです。

### 10.5 数える

```sh
# 管理画面を本番のサーバーの上で作るとき: 記録のフォルダを渡す
npx @devbi/catalog --repo C:\git\reports.git --ref main --view-log D:\devbi\views --out C:\inetpub\catalog

# CI で作るとき: サーバーで数えたファイルを、管理画面から読める場所に置く（1 時間ごとなど）
npx @devbi/catalog views --view-log D:\devbi\views --out C:\inetpub\catalog-views\views.json
```

- 数えたもの（`views.json`）は、ダッシュボードごとの日ごとの「開いた回数」と「見た人の数」と、7・30・90 日の回数と人数です。ログインのない置き方では、人数は出せないので回数だけです。
- **期間の人数は、日ごとの人数を足しては作れません**（同じ人が毎日見ると、30 日で 30 人になってしまう）。期間ごとの人数は、記録を読むときに数えておきます。
- 管理画面（`index.html`）は、作るときに数えたものを中に入れるか、設定の `views:` の場所の `views.json` を読みます。どちらもなければ、閲覧数の欄を出しません。
- 管理画面のフォルダを写し直すとき（`robocopy /MIR`）に消えないよう、`views.json` は管理画面と別のフォルダに置きます。
- ダッシュボードやフォルダの名前を変えたときは、前の名前の記録を、名前の変更の履歴（[7.2](#72-振り分け)）でつなげます。

### 10.6 だれが見たかを残すか

記録のファイルには、利用者の ID を書きます（人数を数えるのに要るため）。管理画面には、既定で**回数と人数だけ**を出し、だれが見たかの名前は出しません。`--with-users` を付けたときだけ、ダッシュボードごとに、見た人と回数の一覧を載せます。

- 社員の閲覧の記録は、個人の情報です。記録を残すことと、何に使うか（使われていないダッシュボードを片付けるため、など）を、社内の決まりに合わせて利用者に知らせます。
- 記録のフォルダは、サービスのアカウントと管理者だけが読めるようにし、`--view-days` で古いものを消します。

### 10.7 静的なサイトの閲覧数（あとで）

IIS などがファイルを配るだけの置き方には、DevBI のサーバーがありません。あとで、次の形を考えています。メモとして残します。

- ブラウザが、開いたときに `GET devbi-view.txt?project=…&dashboard=…`（`dist/` に置く空のファイル）を読む。`#` のあとと違い、`?` のあとは Web サーバーのアクセスログに残る。
- `devbi-catalog` が、IIS のログ（W3C の形。`cs-uri-query` と、Windows 認証の名前の `cs-username`）と nginx のログを読んで数える。IIS のログの時刻は既定で UTC なので、日付の区切りに気をつける。
- ブラウザのキャッシュで 2 回目からが届かないことがないよう、`cache: "no-store"` で読む。

## 11. 設定ファイル（`devbi-catalog.yaml`）

リポジトリのルートに置きます。なくても動きます（プロジェクトの名前はフォルダの名前、リンクはリモートから見分けたもの、本番へのリンクはなし）。

```yaml
# yaml-language-server: $schema=node_modules/@devbi/catalog/catalog.schema.json
title: 社内レポートの管理画面
exclude:
  - packages/create-devbi/template
remote: auto            # auto（既定）/ none / { commit, file, folder, pr }
projects:
  examples/sales:
    title: 売上
    owner: 営業企画 山田
    url: https://reports.corp.local/sales/
  examples/sales/e2e/rls:
    title: 担当別の売上
    url: https://app.corp.local/my
views: ../catalog-views/views.json   # 管理画面から見た views.json の場所（10.5）
```

| キー | 中身 |
| --- | --- |
| `title` | 管理画面の見出し。既定は「DevBI 管理画面」 |
| `exclude` | プロジェクトにしないフォルダ（雛形、テストの材料など）。`*` と `**` が使える |
| `remote` | リモートへのリンクの形（[8 章](#8-リモートへのリンク)） |
| `projects.<場所>.title` / `owner` / `description` | プロジェクトの名前、担当、説明 |
| `projects.<場所>.url` | 本番の場所（[9 章](#9-公開先へのリンク)） |
| `projects.<場所>.dashboards.<名前>` | ダッシュボードごとの本番の場所 |
| `views` | `views.json` の場所 |

設定は、プロジェクトごとのファイルではなく、ルートの 1 つにまとめます。置き場所や担当は、プロジェクトを作る人より管理者が決めることが多く、1 か所で見られるほうが直しやすいためです（[15 章](#15-決めること確かめること)の 4）。

## 12. 置き場所と、見られる人

### 12.1 管理者だけが入れる場所に置く

管理画面には、SQL の中身、行レベル制御の決まり、役割の名前、接続先の名前、コミットした人の名前が入ります。**管理者だけが入れる場所**に置きます。

- **IIS**: サイトかフォルダに Windows 認証をかけ、承認規則で管理者のグループだけを許します（[静的なサイトの手順](../deploying.md#手順の例windows-の-iis)と同じやり方）。
- **ファイル共有**: `index.html` 1 つに、データも中に入っているので、ファイルとして開いても動きます（DevBI のダッシュボードと違い、`file://` でも開けます）。共有フォルダのアクセス権を管理者だけにします。ただし、別の場所の `views.json` を読めるのは Web サーバーから開いたときだけです（ファイルで開くなら、作るときに閲覧数を中に入れる）。
- **Azure DevOps・GitHub**: パイプラインの成果物（artifact）として残すと、リポジトリを見られる人だけがダウンロードできます。
- **GitHub Pages には置きません。** 非公開のリポジトリからの Pages も、Enterprise の「非公開の Pages」でない限り、だれでも見られる公開のサイトになります。

載せないものも選べます: `--no-sql` で SQL の中身を載せません。メールアドレス（`--emails`）と見た人の名前（`--with-users`）は、既定では載せません。

### 12.2 いつ作るか

リポジトリの main が変わったとき（CI）か、決まった時刻（サーバーのタスク）に作り直します。閲覧数は記録が増えるたびに変わるので、`devbi-catalog views` を 1 時間ごとなどに動かします。

### 12.3 作り方の例

作るときに確かめてから、deploying.md に書きます。

GitHub Actions（社内のサーバーに写すので、社内の runner で）:

```yaml
on:
  push: { branches: [main] }
jobs:
  catalog:
    runs-on: [self-hosted, windows]
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }          # 浅い clone だと履歴が切れる（7.3）
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npx --yes @devbi/catalog --out catalog --strict
      - run: robocopy catalog \\web01\catalog$ /MIR; if ($LASTEXITCODE -ge 8) { exit 1 } else { exit 0 }   # robocopy は 1〜7 も成功
```

Azure Pipelines:

```yaml
trigger: [main]
pool: { name: 社内 }                        # 社内のエージェント
steps:
  - checkout: self
    fetchDepth: 0                            # 浅い clone だと履歴が切れる（7.3）
  - task: UseNode@1
    inputs: { version: 22.x }
  - script: npx --yes @devbi/catalog --out $(Build.ArtifactStagingDirectory)/catalog --strict
  - publish: $(Build.ArtifactStagingDirectory)/catalog
    artifact: catalog                        # リポジトリを見られる人だけがダウンロードできる
```

社内サーバーの bare リポジトリ（タスクスケジューラで 10 分ごとなど）:

```bat
npx --yes @devbi/catalog --repo C:\git\reports.git --ref main --view-log D:\devbi\views --out C:\inetpub\catalog
```

- ファイル共有に置いた bare リポジトリ（`\\server\git\reports.git`）では、`post-receive` のフックは、push した人のパソコンで動きます（共有のフォルダに、各自のパソコンの git が直接書くため）。フックではなく、サーバーのタスクで作ります。
- SSH でつなぐ bare リポジトリなら、`post-receive` のフックで作ることもできます。push の答えを待たせないよう、後ろで動かします。

## 13. 落とし穴と対策（まとめ）

| 落とし穴 | 対策 |
| --- | --- |
| CI の浅い clone で、履歴が途中で切れていることに気づかない | `--is-shallow-repository` で確かめて画面に出す。`--strict` で止める。CI の例に `fetch-depth: 0` |
| 管理画面に SQL や行レベル制御の決まりが載り、見せたくない人に見える | 管理者だけの場所に置く。GitHub Pages には置かない。`--no-sql` |
| リモートの URL のトークンが管理画面に書かれる | リモートの URL はそのまま書かない。ユーザー名とパスワードを除いた Web の場所だけ |
| `.env.local` のパスワードや、コミットしていないファイルが入る | コミットの中身だけを git から読む。`.env` からは変数の名前とデータベースの種類だけ |
| 日本語のファイル名が `"\346…"` になる、リンクが切れる | `-z` と `core.quotePath=false`。リンクのパスは 1 つずつ URL の形に |
| マージ コミットの多いリポジトリで、PR の中の細かいコミットが並ぶ | `--first-parent` で、main に入った単位にする |
| 同じ人が別の名前で出る | `.mailmap` |
| 雛形やテストの材料がプロジェクトに見える | `exclude` |
| プロジェクトの中のプロジェクトの変更が、外側の履歴にも出る | いちばん内側のプロジェクトにだけ入れる |
| 名前を変えたダッシュボードの履歴と閲覧数が切れる | 名前の変更をたどってつなぐ。前の URL が開けなくなったことも出す |
| どのダッシュボードかが、Web サーバーのログに残らない（`#` のあとは送られない） | ブラウザが `POST api/view` で送る |
| 期間の人数を、日ごとの人数の和で出してしまう | 期間ごとの人数は、記録を読むときに数える |
| 閲覧の記録で、ディスクがいっぱいになる | ログインした人の同じダッシュボードは 1 分に 1 行、全部で 1 分に 600 行、1 日 50 MB、古いファイルを消す |
| 前に IIS や nginx を置くと全員が同じ IP アドレスに見え、IP アドレスで分けると閲覧を落とす | ログインしていない人は IP アドレスで分けず、全部の上限だけにする |
| 閲覧数を増やされる | 目安として使う（厳密な記録ではない）と書く。ほかのサイトからは送れない（JSON で送る） |
| 開発中の閲覧が数に入る | 開発サーバーと `vite preview` は書かない。検証と本番でフォルダを分ける |
| 社員の閲覧の記録を、知らせずに残す | 既定は書かない（`--view-log` を付けたときだけ）。管理画面には既定で名前を出さない。社内の決まりに合わせて知らせる |
| 2 つのプロセスが同じ記録のファイルに書いて、行が混ざる | 1 つのフォルダに 1 つのプロセス。C# は `OnView` でアプリのログに渡せる |
| `robocopy /MIR` で、管理画面のフォルダの `views.json` が消える | `views.json` は別のフォルダに置き、設定の `views:` で場所を書く |
| ファイル共有の bare リポジトリのフックが、push した人のパソコンで動く | サーバーのタスクで作る |

## 14. 作る順番（PR の分け方）

1. **カタログの中身（`catalog.json`）**: 新しいパッケージ `@devbi/catalog`（公開するパッケージが 7 つになるので、`scripts/version.mjs`・`publish.mjs`・`check:packed` も直す）。コミットの中身を git から読む、プロジェクトを見つける、`readProject`・`parseDataset` で読む、つながり、`git log` を 1 回読んで振り分ける（名前の変更、消したもの、浅い clone）、リモートの見分けとリンク（8.1 の表をテストの材料にする）、設定ファイルと JSON Schema、`devbi-catalog --json`。`readProject` のある `@devbi/vite` は DuckDB-wasm などの重い依存を連れてくるので、読む部分だけを軽いパッケージに移すかを決める。テストは、一時フォルダに git のリポジトリを作り、日時と人を決めたコミットを積んで確かめる（日本語のファイル名、マージ コミット、名前の変更、浅い clone、bare リポジトリ）。reference.md に「管理画面（devbi-catalog）」の節を足す。
2. **画面**: `index.html` 1 つ（React と Vite でビルドしてパッケージに入れておく。DuckDB-wasm は使わない）。全体・プロジェクト・ダッシュボード・変更の履歴の 4 つの画面、`--open`（作って開く）、`--no-sql`、`--strict`。このリポジトリ（公開している OSS）の管理画面を、ドキュメントのサイトの `/devbi/catalog/` に置いて見られるようにする（ライブデモと同じ `pages.yml`）。e2e と manual-check.md。
3. **置き方の手順**: deploying.md に「管理画面を置く」（管理者だけの場所、GitHub Actions・Azure Pipelines・社内サーバーのタスクの例、浅い clone、`robocopy`）。小さければ 2 に入れる。
4. **閲覧の記録（Node と `devbi-serve`）**: ブラウザの `views: true` と `POST api/view`、`@devbi/vite` が入れる `project`、Node の `views` と `fileViews`、`devbi-serve --view-log`・`--view-days`、守り（[10.4](#104-守り)）、`devbi-catalog views`、閲覧数の画面。Next.js の見本に `views` を足す。ドキュメントのサイトの管理画面には、作ったサンプルの閲覧数を入れる（サンプルだと画面に書く）。
5. **閲覧の記録（C#）**: `DevBIOptions.ViewLog`・`OnView`、`HttpContext.User` からの利用者、パリティのテスト（`project`・`dashboard` の確かめと、記録の 1 行の形）。
6. あとで: 静的なサイトの閲覧数（[10.7](#107-静的なサイトの閲覧数あとで)）、本番に出ている版（ビルドのときに `dist/devbi-build.json` にコミットを書き、管理画面が読んで「本番は 3 コミット前」と出す。管理画面とダッシュボードのオリジンが違えば CORS が要る）、`devbi-check` のファイルの検査の結果、差分、CODEOWNERS から担当、リモートでファイルを直す画面へのリンク（GitHub の `/edit/`、Azure DevOps の編集）。

## 15. 決めること・確かめること

利用者に決めてもらいたいこと:

1. **管理画面の形**: リポジトリから作る静的なサイト（`devbi-catalog`。この設計）でよいか。ほかの案は、`devbi-serve` の中に管理画面を足す形です（いつも最新で、閲覧数もその場で読めるが、`devbi-serve` を使わない置き方（静的なサイト、ASP.NET のアプリ）では使えない）。**勧め: 静的なサイト。** どの置き方とも組み合わせられ、GitHub・Azure DevOps・bare リポジトリで同じに動くため。
2. **会社での置き方**: 会社では、DevBI をどう置きそうか（IIS の静的なサイト / `devbi-serve` / ASP.NET のアプリに埋め込み）。閲覧数をどこから数えるかの順番が変わります。**勧め: まず DevBI のサーバー（`devbi-serve`・Node・C#）が書く形（14 章の 4・5）。** 静的なサイトのアクセスログから数える形（10.7）は、IIS のログで確かめられてから。
3. **見た人の名前**: 管理画面に、だれが見たかを出すか。**勧め: 既定は回数と人数だけ。** 名前は `--with-users` を付けたときだけ。
4. **設定の置き場所**: リポジトリのルートの `devbi-catalog.yaml` 1 つか、プロジェクトごとのファイルか。**勧め: ルートの 1 つ**（[11 章](#11-設定ファイルdevbi-catalogyaml)）。
5. **最初に作る範囲**: 14 章の 1〜3（閲覧数なしの管理画面）を先に作り、閲覧数（4・5）は 2 が決まってから、でよいか。**勧め: そのとおり。** 1〜3 は、会社の置き方によらず使えるため。

作るときに確かめること:

- Azure DevOps（クラウドと、社内に置く Azure DevOps Server）の、コミット・ファイル・フォルダ・PR の URL の形と、取り込んだときのコミットの見出しの形（`Merged PR 123: …`）。
- Azure Pipelines の既定の clone の深さ（`fetchDepth`）と、パイプラインの設定画面の「浅い取得」が YAML より優先されるか。
- `fetch` の `keepalive` が、Windows 認証（NTLM・Kerberos）のサイトで、ページを閉じる間際にも届くか。
- 大きなリポジトリ（コミット 1 万、ファイル 10 万）で、`git log` と `git cat-file --batch` が何秒かかるか。
- IIS の W3C ログの `cs-username` に、Windows 認証の名前が入ること（10.7 のため）。

## 付録: ほかの BI・道具との違い

- **Power BI**: サービスに、ワークスペースの中のものの一覧、データセットとレポートのつながりを見る「系列ビュー（lineage view）」、レポートごとの閲覧数と閲覧者数を出す「使用状況メトリック」、管理者向けの管理ポータルと監査のログがあります。DevBI の管理画面は、このうち一覧・つながり・閲覧数を、リポジトリと DevBI のサーバーの記録から作ります。権限やテナントの設定はしません（2026-11 時点の理解。作るときに確かめます）。
- **dbt docs**: dbt のプロジェクトから、モデルの一覧とつながり（系列）を静的なサイトとして作ります。`devbi-catalog` も、同じ「リポジトリから静的なサイトを作る」形です。dbt docs と違い、git の履歴と閲覧数を入れます。
- **Backstage**: リポジトリの中のファイル（`catalog-info.yaml`）を決まりで読んで、社内のソフトウェアの一覧を作ります。`devbi-catalog` は、DevBI のファイルの形（`dashboards/*.dash.json`）そのものを決まりにするので、足すファイルは要りません。
- **Metabase**: 閲覧数などの使われ方の分析（Usage analytics）は、有料版の機能です（2026-11 時点の理解。作るときに確かめます）。DevBI では、MIT のまま使えるようにします。
